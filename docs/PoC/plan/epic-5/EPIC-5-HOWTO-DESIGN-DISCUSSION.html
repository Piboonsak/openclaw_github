pytesseract — Pros / Cons

  • Pros: Simple dependency stack and stable baseline behavior.
  • Pros: Mid-tier confidence and moderate text coverage.
  • Cons: Slower than PaddleOCR in this benchmark.
  • Cons: Lower Thai-specific quality metrics than PaddleOCR.

EasyOCR — Pros / Cons

  • Pros: Captures Thai characters well (highest Thai ratio among engines).
  • Pros: Works without cloud APIs.
  • Cons: Very slow on CPU (avg ~222s/doc) and throughput-unfriendly.
  • Cons: Lowest confidence and lowest heuristic score in this run.

PaddleOCR — Pros / Cons

  • Pros: Best overall quality metrics (heuristic score, confidence, keyword hit).
  • Pros: Faster than both pytesseract and EasyOCR in this run.
  • Cons: Runtime stack is heavier and required version pinning in this environment.
  • Cons: More setup complexity for reproducible local environments.
Claude model version and routing trigger
Plan references Claude 3.5 Haiku/Sonnet (outdated). Should use Claude 4.x. Need to define what makes a doc "complex" to trigger model upgrade.
Recommend: Default Haiku 4.5, upgrade to Sonnet 4.6 when: (a) page_count > 3, (b) OCR confidence < 80%, or (c) first extraction attempt has >2 low-confidence fields.
Journal Router: rule-based vs LLM-assisted for variable accounts
is_variable: true entries in rule_coa.yaml need expense account code (5xxx-xx) determined by vendor/description. Prototype uses vendor-name matching. LLM could classify but adds cost/latency.
Recommend: Hybrid — deterministic rules and vendor lookup first, fuzzy similarity second, LLM semantic assist only when unresolved, then human confirmation writes back to mapping cache.
D3 Design Logic + Code Skeleton (discussion-only)

This design separates onboarding intelligence from runtime determinism. COA + mapping guideline files are ingested asynchronously once, while runtime routing minimizes LLM calls and learns from confirmed user decisions in Map Review.

Runtime Resolver Tiers

  • Tier 1: Canonical exact match (vendor/item normalized text)
  • Tier 2: Similarity match (Jaro-Winkler or token overlap)
  • Tier 3: LLM account suggestion from company COA context
  • Map Review always shown for unresolved or low confidence

Learning Loop

  • User approves or edits suggested expense account
  • System writes confirmation to company mapping cache
  • Future transactions route deterministically at Tier 1
  • LLM usage and latency decrease over time
Approach Accuracy stability Latency/cost Maintainability Recommendation
Rule-only Medium Low Medium Good baseline, weak for unseen vendors
LLM-only Medium High Low Not preferred for production accounting posting
Hybrid (proposed) High Medium High Best fit for PoC to MVP transition 
# D3 skeleton (discussion only)
def resolve_variable_account(tx, company_ctx):
    key = normalize_vendor_item(tx.vendor_name, tx.line_description)

    # Tier 1: deterministic cache
    hit = mapping_cache_get(company_ctx.company_id, key)
    if hit:
        return {"account_code": hit, "source": "cache_exact", "confidence": 0.99}

    # Tier 2: local similarity (no LLM)
    sim = mapping_cache_similarity_lookup(company_ctx.company_id, key, threshold=0.90)
    if sim:
        return {"account_code": sim.account_code, "source": "cache_fuzzy", "confidence": sim.score}

    # Tier 3: LLM fallback using only company COA candidates
    llm = suggest_account_from_coa(tx, company_ctx.chart_of_accounts)
    return {"account_code": llm.account_code, "source": "llm_assist", "confidence": llm.confidence, "needs_review": True}

def on_map_review_confirmed(company_id, key, approved_account_code):
    mapping_cache_upsert(company_id, key, approved_account_code)
Rule matching precedence
A document could match multiple rules (e.g., Invoice matches both RRL-PURCHASE-SUPPLIES and RRL-EXPENSE-CREDIT). Need clear precedence logic.
Recommend: Score-based matching — count condition matches, highest score wins. Tie-breaker: most specific rule (most conditions defined) wins.
D4 Matching Precedence + Scoring Skeleton (discussion-only)

To avoid non-deterministic posting, each candidate rule gets a weighted score. Highest score wins. Ties are resolved by specificity (rule with more explicit conditions).

Suggested Weighting

  • document_type match: +20
  • payment_method match: +20
  • source_document match (e.g., P/O): +25
  • has_vat, vat_type, has_wht: +10 each
  • Condition mismatch for hard constraints: candidate rejected

Safety Behavior

  • No candidate pass: mark voucher UNRESOLVED_RULE
  • Tie after specificity: route with ambiguous_rule flag
  • Always run final Dr/Cr balance validation before output
# D4 skeleton (discussion only)
def pick_best_rule(extraction, compiled_rules):
    scored = []
    for rule in compiled_rules:
        score, matched, rejected = score_rule(rule, extraction)
        if rejected:
            continue
        scored.append({
            "rule": rule,
            "score": score,
            "specificity": count_defined_conditions(rule),
            "matched": matched,
        })

    if not scored:
        return {"status": "UNRESOLVED_RULE", "needs_review": True}

    scored.sort(key=lambda r: (r["score"], r["specificity"]), reverse=True)
    winner = scored[0]
    return {
        "status": "OK",
        "rule_id": winner["rule"].rule_id,
        "score": winner["score"],
        "specificity": winner["specificity"],
        "needs_review": (len(scored) > 1 and scored[0]["score"] == scored[1]["score"]),
    }
"รายงานรับ" / "รายงานจ่าย" scope
Scope should include platform settlement statements (example in Comp_2/6904-เมเจอร์) that summarize gross sales, commissions, fee VAT, and net payout. These can drive revenue-side GL posting logic.
Recommend: Treat this as dual-scope — (1) settlement-driven journal rules for platform income posting and (2) derived purchase/sales VAT reports generated from finalized journal lines.
D5 Platform Settlement Mapping + Posting Skeleton (discussion-only)

For files like 3-C6LKDCCVLXDTE2-20260401.pdf, extraction should normalize settlement fields first, then route through a dedicated posting template for platform channels.

Normalized Settlement Fields

  • gross_sales_amount
  • platform_commission_amount
  • platform_fee_vat_amount
  • withholding_tax_amount (if any)
  • net_payout_amount

Posting Pattern (example)

  • Dr Bank = net payout received
  • Dr Platform commission expense
  • Dr Input VAT on platform fee
  • Cr Service revenue (gross)
  • Cr Output VAT / Cr WHT payable as applicable
# D5 skeleton (discussion only)
def route_platform_settlement(doc):
    x = normalize_settlement_fields(doc)

    entries = []
    entries.append(dr("1113-01", x.net_payout_amount))
    entries.append(dr("5xxx-commission", x.platform_commission_amount))

    if x.platform_fee_vat_amount > 0:
        entries.append(dr("1154-00", x.platform_fee_vat_amount))

    entries.append(cr("4100-01", x.gross_sales_amount))

    if x.output_vat_amount > 0:
        entries.append(cr("2135-00", x.output_vat_amount))
    if x.withholding_tax_amount > 0:
        entries.append(cr("2132-03", x.withholding_tax_amount))

    assert is_balanced(entries), "Settlement posting must balance"
    return entries

Edge cases to include in final rule spec: reversal lines, month-end adjustments, negative commission corrections, and missing VAT columns in some platform formats.

Multi-company rule architecture
rule_coa.yaml is company-specific (ฤทธิ์ล้ำเลิศ). Prototype supports 2 companies. Need structure for per-company COA + shared rule templates.
Recommend: rules/global/ for shared journal patterns + rules/{company_id}/rule_coa.yaml for per-company COA and overrides.
Backend-frontend integration
Prototype is self-contained HTML/JS with hardcoded data. Backend outputs JSON to cache/. No API layer exists.
Recommend for PoC: Python script processes batch → writes results to JSON → frontend reads static JSON files. Full API layer deferred to MVP.
Accuracy evaluator scope
Plan only measures header field accuracy (Tax ID, invoice#, amounts). Doesn't measure journal entry posting accuracy (correct account codes, balanced Dr/Cr).
Recommend: Add journal-level metrics — account_code accuracy per line, balance check pass rate, and full-voucher match rate.
