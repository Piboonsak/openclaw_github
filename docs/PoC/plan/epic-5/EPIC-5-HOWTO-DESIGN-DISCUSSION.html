1. Architecture Overview

The pipeline is designed to minimise LLM calls by resolving as much as possible through deterministic stages (OCR → template → rules) before escalating to Claude. Only ~15–25 % of documents should reach Stage D in steady state.

# src/pipeline/orchestrator.py
from dataclasses import dataclass
from enum import Enum, auto

class StageResult(Enum):
    PASS = auto()        # proceed to export
    ESCALATE_LLM = auto()   # → Stage D
    ESCALATE_HUMAN = auto() # → Stage E
    FEEDBACK = auto()    # → Stage F (async)

@dataclass
class PipelineContext:
    doc_id: str
    ocr_result: "OcrResult"            # Stage A output
    template_match: "TemplateMatch"    # Stage B output
    extraction: "Extraction"           # Stage C output
    llm_result: "LlmExtraction | None" # Stage D output (if called)
    review: "ReviewDecision | None"    # Stage E output (if escalated)

async def run_pipeline(image_path: str) -> PipelineContext:
    """Main orchestrator — runs stages A→F with early exit."""
    ctx = PipelineContext(doc_id=gen_id(), ...)

    # ── Stage A: OCR ──
    ctx.ocr_result = await ocr_engine.process(image_path)
    if ctx.ocr_result.avg_confidence < 0.60:
        return escalate_human(ctx, reason="OCR too low")

    # ── Stage B: Template Classify ──
    ctx.template_match = template_classifier.classify(ctx.ocr_result)

    # ── Stage C: Rule Extraction ──
    if ctx.template_match.match_score >= TEMPLATE_THRESHOLD:
        ctx.extraction = rule_extractor.extract(ctx.ocr_result, ctx.template_match)
        if ctx.extraction.all_confident():
            await feedback_loop.record_success(ctx)  # Stage F
            return ctx  # ✅ DONE — no LLM needed
    
    # ── Stage D: Claude LLM ──
    model = select_model(ctx)  # see routing policy below
    ctx.llm_result = await claude_extract(ctx, model=model)
    
    if ctx.llm_result.has_unresolved():
        return escalate_human(ctx, reason="LLM unresolved")

    # ── Stage F: Feedback ──
    await feedback_loop.learn(ctx)
    return ctx  # ✅ DONE

def select_model(ctx: PipelineContext) -> str:
    """Production routing policy — see §Routing Policy below."""
    if ctx.ocr_result.page_count > 3:
        return "claude-sonnet-4-20250514"
    if ctx.ocr_result.avg_confidence < 0.80:
        return "claude-sonnet-4-20250514"
    if ctx.extraction and ctx.extraction.low_confidence_fields > 2:
        return "claude-sonnet-4-20250514"
    return "claude-haiku-4-20250414"

D3 Design Logic + Code Skeleton (discussion-only)

This design separates onboarding intelligence from runtime determinism. COA + mapping guideline files are ingested asynchronously once, while runtime routing minimizes LLM calls and learns from confirmed user decisions in Map Review.

Runtime Resolver Tiers

  • Tier 1: Canonical exact match (vendor/item normalized text)
  • Tier 2: Similarity match (Jaro-Winkler or token overlap)
  • Tier 3: LLM account suggestion from company COA context
  • Map Review always shown for unresolved or low confidence

Learning Loop

  • User approves or edits suggested expense account
  • System writes confirmation to company mapping cache
  • Future transactions route deterministically at Tier 1
  • LLM usage and latency decrease over time

def resolve_variable_account(tx, company_ctx):
    key = normalize_vendor_item(tx.vendor_name, tx.line_description)

    # Tier 1: deterministic cache
    hit = mapping_cache_get(company_ctx.company_id, key)
    if hit:
        return {"account_code": hit, "source": "cache_exact", "confidence": 0.99}

    # Tier 2: local similarity (no LLM)
    sim = mapping_cache_similarity_lookup(company_ctx.company_id, key, threshold=0.90)
    if sim:
        return {"account_code": sim.account_code, "source": "cache_fuzzy", "confidence": sim.score}

    # Tier 3: LLM fallback using only company COA candidates
    llm = suggest_account_from_coa(tx, company_ctx.chart_of_accounts)
    return {"account_code": llm.account_code, "source": "llm_assist", "confidence": llm.confidence, "needs_review": True}

Rule matching precedence
A document could match multiple rules (e.g., Invoice matches both RRL-PURCHASE-SUPPLIES and RRL-EXPENSE-CREDIT). Need clear precedence logic.
Decision: Score-based matching — count condition matches, highest score wins. Tie-breaker: most specific rule (most conditions defined) wins.
D4 Matching Precedence + Scoring Skeleton (discussion-only)

To avoid non-deterministic posting, each candidate rule gets a weighted score. Highest score wins. Ties are resolved by specificity (rule with more explicit conditions).

Suggested Weighting

  • document_type match: +20
  • payment_method match: +20
  • source_document match (e.g., P/O): +25
  • has_vat, vat_type, has_wht: +10 each
  • Condition mismatch for hard constraints: candidate rejected

Safety Behavior

  • No candidate pass: mark voucher UNRESOLVED_RULE
  • Tie after specificity: route with ambiguous_rule flag
  • Always run final Dr/Cr balance validation before output

            "rule": rule,
            "score": score,
            "specificity": count_defined_conditions(rule),
            "matched": matched,
        })

    if not scored:
        return {"status": "UNRESOLVED_RULE", "needs_review": True}

    scored.sort(key=lambda r: (r["score"], r["specificity"]), reverse=True)
    winner = scored[0]
    return {
        "status": "OK",
        "rule_id": winner["rule"].rule_id,
        "score": winner["score"],
        "specificity": winner["specificity"],
        "needs_review": (len(scored) > 1 and scored[0]["score"] == scored[1]["score"]),
    }

Confidence Scoring Methodology

Signal Weight Measurement Scoring
LLM self-report 30% Claude confidence field per extraction 0-100 from model output
Multi-pass agreement 25% Run extraction 2x, compare outputs 100 if identical, -20 per disagreement
COA cross-reference 20% All account_codes in entries exist in COA list 100 if all valid, 0 per missing code
Dr/Cr balance check 15% Debit total == Credit total per rule 100 if balanced, 0 if not
Source text coverage 10% % of rule fields traceable to source text Proportional to fields with source match

Thresholds: ≥90% = auto-approve (green ✓), 75-89% = flag for review (amber ⚠), <75% = requires human editing (red ✗)

Key Design Principles

  • Idempotent regeneration: Re-uploading same files yields same output (SHA-256 cache). Changed files trigger full re-generation.
  • Human-in-the-loop: Rules below 90% confidence require explicit approval before use in journal routing (TASK-503).
  • Audit trail: Every generation preserves source files, LLM prompts/responses, and validation results.
  • Incremental update: Future: edit individual rules without regenerating entire file. Track last_modified_by: human|llm per rule.
  • Multi-company isolation: Each company's rules directory is independent. No cross-contamination of COA codes.
  • Graceful degradation: If generation fails mid-pipeline, partial results are saved with clear error markers. No silent data loss.

Key Design Principles

  • Same-origin simplicity: Path-based routing eliminates CORS complexity and multi-cert management in production.
  • Graceful degradation: WebSocket with polling fallback ensures Step 3 works even behind restrictive proxies.
  • Stateless workers: Celery workers can be scaled independently without session affinity.
  • Environment parity: Docker Compose for both dev and prod — same service topology, different configs.
  • Zero-downtime deploy: docker compose pull && up -d with health check gates before traffic switch.
  • Audit-first: Every state transition logged; all human edits tracked with before/after diffs.
Accuracy evaluator scope
Plan only measures header field accuracy (Tax ID, invoice#, amounts). Doesn't measure journal entry posting accuracy (correct account codes, balanced Dr/Cr). D6 generates rules but no feedback loop to improve them from human review.
Decision: Add journal-level metrics — account_code accuracy per line, balance check pass rate, and full-voucher match rate. Connect D6 rule output to D8 evaluator. Capture user corrections as reinforcement signal to improve rules iteratively.

from dataclasses import dataclass
from enum import Enum
from typing import Optional

class MatchLevel(Enum):
    FIELD = "field"           # Individual field (tax_id, amount, date)
    ACCOUNT = "account"       # COA account code per journal line
    JOURNAL = "journal"       # Full voucher structure (Dr/Cr balance)
    RULE = "rule"             # End-to-end rule effectiveness

@dataclass
class EvalResult:
    level: MatchLevel
    rule_id: str
    predicted: str
    expected: str
    is_match: bool
    confidence: float
    match_type: str           # "exact" | "fuzzy" | "tolerance"

def evaluate_document(prediction: dict, ground_truth: dict, rules: dict) -> list[EvalResult]:
    """Compare prediction vs ground truth at all 4 levels."""
    results = []

    # Level 1: Field accuracy
    for field in ["tax_id", "invoice_no", "date", "total_amount", "vat_amount"]:
        results.append(compare_field(field, prediction, ground_truth))

    # Level 2: Account code accuracy
    for i, line in enumerate(prediction.get("journal_lines", [])):
        gt_line = find_matching_gt_line(line, ground_truth["journal_lines"])
        results.append(compare_account(line, gt_line))

    # Level 3: Journal structure accuracy
    results.append(check_journal_structure(prediction, ground_truth))

    # Level 4: Rule effectiveness
    rule_id = prediction.get("applied_rule_id")
    results.append(evaluate_rule(rule_id, results))

    return results

    if correction_rate > 0.20 or rule.get("corrected", 0) >= 5:

def queue_rule_improvement(rule_id: str, reason: str):
    """Queue a rule for LLM-powered re-generation using corrections as examples."""
    corrections = load_corrections_for_rule(rule_id)

    # Build few-shot examples from user corrections
    few_shot_examples = []
    for c in corrections[-10:]:  # Last 10 corrections as context
        few_shot_examples.append({
            "document_context": c["context_snippet"],
            "wrong_mapping": c["predicted"],
            "correct_mapping": c["corrected"],
            "field": c["field"]
        })

    # Create improvement request (picked up by D6 pipeline)
    request = {
        "rule_id": rule_id,
        "reason": reason,
        "current_accuracy": calculate_rule_accuracy(rule_id),
        "correction_examples": few_shot_examples,
        "company_id": get_company_for_rule(rule_id),
        "status": "pending_generation",  # → "candidate" → "approved" → "promoted"
    }
    save_improvement_request(request)

def regenerate_rule_with_feedback(request: dict) -> dict:
    """
    Re-invoke D6 LLM pipeline with correction examples injected into prompt.

      System: You are a Thai accounting rule generator...
      Context: Company COA + existing rules

    existing_rule = load_current_rule(company_id, request["rule_id"])
    corrections = request["correction_examples"]

        base_rule=existing_rule,

    )

    candidate = call_llm_structured(prompt, schema="rule_coa_entry")

    return {

        "validation": validation,
        "ab_score": ab_score,
        "status": "awaiting_human_approval" if ab_score > 0.7 else "auto_rejected"

Key Design Principles

  • Append-only correction logs: corrections_log.jsonl is immutable. Never delete or modify past corrections — they form the training signal.
  • Human-in-the-loop gate: No rule is auto-promoted. Every candidate must pass A/B test AND receive human approval before replacing the active rule.
  • Gradual improvement: Rules improve incrementally per company. Each correction makes future extractions more accurate for that specific company's patterns.
  • Transparency: Users see which rule was applied, its accuracy stats, and how their corrections contribute. Builds trust in the system.
  • Versioned rules: Every rule version is preserved. Rollback is instant if a promoted rule performs worse than expected.
  • D6 reuse: Rule improvement uses the same LLM pipeline from D6 (Stage 2 + Stage 3) — just with enhanced prompts that include correction examples as few-shot context.
  • Privacy-safe: Correction logs store field values and context snippets only — no full document content. Sufficient for retraining without data retention risk.
Multi-Provider LLM Router (OpenRouter Gateway)
Current pipeline locks every LLM call (Stage A repair, D6 rule generation, Stage C extraction, ground-truth labeling) to Anthropic native SDK with a single model. Risks: vendor lock-in, no cost-tier ladder, no ensemble option, single point of outage. relabel_with_haiku.py proved we can swap models freely — now we generalize that lesson across the whole pipeline.
Decision: Introduce llm_router.py + providers/ package using OpenRouter as the primary gateway with Anthropic native SDK as fallback. Current implementation focus is per-field cascade: regex output first, then free models, then paid models (Haiku/Sonnet) only for unresolved critical fields.

@dataclass
class LLMResponse:
    fields: dict          # parsed JSON output
    confidence: float     # 0.0–1.0, normalized across providers
    tokens_in: int
    tokens_out: int

    def health_check(self) -> bool: ...

def pick_provider(use_case: str, complexity: str = "med") -> tuple[LLMProvider, str]:
    """Returns (provider_instance, model_name) per routing policy."""
    policy = _REGISTRY["routes"][use_case][complexity]
    provider = _get_provider(policy["provider"])
    return provider, policy["model"]

async def extract(pdf_bytes: bytes, hint: str = "extraction",
                  complexity: str = "med") -> LLMResponse:
    primary, model = pick_provider(hint, complexity)
    check_budget()
    try:
        resp = await primary.call(pdf_bytes, SYSTEM_PROMPT, USER_PROMPT, model)
    except (ProviderError, TimeoutError):
        fallback, fb_model = pick_provider(hint, complexity, fallback=True)
        resp = await fallback.call(pdf_bytes, SYSTEM_PROMPT, USER_PROMPT, fb_model)
    log_call(resp)
    return resp

Key Design Principles

  • Provider-agnostic core: Pipeline code (orchestrator, field_extractor, rule_generator) never imports Anthropic or OpenAI SDK directly. Only llm_router + providers/* know about specific vendors.
  • Fail-safe fallback chain: Outage of one provider ≠ pipeline outage. Each route declares primary + fallback in model_registry.yaml.
  • Cost-observable: Every call logged with provider, model, tokens, USD. Daily/weekly aggregation exposed via API.
  • Cache-isolated: Cache key includes provider+model. No cross-pollution between Sonnet results and Opus results during A/B runs.
  • Backward-compat: call_claude_repair() and other legacy callsites remain functional via thin wrappers. New code uses llm_router.extract().
  • Schema-stable: Unified LLMResponse dataclass regardless of provider. Downstream code does not branch on provider type.
  • Phased rollout: Each phase has explicit decision gate (accuracy / cost) before proceeding. Phase 3 ensemble is opt-in per document, not always-on.
  • Reuse D6 pattern: rule_generator.py already implements a multi-provider fallback router (Anthropic → OpenAI → OpenRouter). D9 generalizes that pattern and migrates D6 to use it.

VAT Layout-Aware Reconciliation & Money-Field Trust Policy
Two new regressions showed a critical trust bug: docs 03062026125316 and 03062026125326 had clear printed VAT values, but Stage C replaced them with calculated values. Root cause: the mismatch rule in extraction only validated the exclusive layout (net + vat = total), so valid inclusive docs were marked mismatched, confidence dropped, and Stage C overwrote a correct VAT with a computed value.
Decision: printed money values are the primary truth. Apply three-layer protection: (1) layout-aware mismatch logic, (2) OCR-presence gate for Stage C money merges, (3) prompt-level prohibition against computing numeric fields.
D10 Design Details — Thai VAT Formula, 3-Layer Defense, and Expected Outcomes (click to expand)

Thai VAT Formula (must handle both layouts)

  • Exclusive (บวก VAT): VAT = Net × 7%, Gross = Net + VAT = Net × 1.07
  • Inclusive (ถอด VAT): VAT = Gross × 7 / 107, Net = Gross × 100 / 107

Important: Gross × 7% is not the inclusive VAT formula. Using it causes the exact wrong value seen in doc 03062026125316 (139.30 instead of printed 130.19).

Three-Layer Defense

LayerChangeExpected Effect
Layer 1
Extractor Gate		 src/backend/ml/field_extractor.py: change vat_math_mismatch to pass when either exclusive or inclusive arithmetic fits within tolerance. Inclusive docs no longer get false mismatch flag. Stage C is not triggered for valid printed VAT.
Layer 2
Router Merge Gate		 src/backend/ml/llm_router.py: in _merge_improvements(), reject money-field candidate if value is not found in OCR text (_value_in_ocr). Computed money values from LLM cannot overwrite extracted values.
Layer 3
Prompt Policy		 src/backend/ml/llm_claude.py: explicitly forbid deriving or recalculating money fields in Stage C prompt. Model behavior is aligned with pipeline trust policy before merge-time checks.
