ระบบ: LedgerFlow - Scan Review
ช่วงงาน: Phase II (Enhancement & Edge Cases)
เวอร์ชันเอกสาร: v1.0
วันที่: 2026-06-09

ภาพรวมปัญหาที่จะพัฒนา

WHT extraction/consistency VAT layout classification Thai label ambiguity (NET/TOTAL) OCR overlap/gridline noise Broker-specific document template Review UX Zone B width
เป้าหมายหลัก: ลดการตีความผิดระหว่าง บวก VAT (exclusive) กับ ถอด VAT (inclusive), เพิ่มความน่าเชื่อถือในเอกสารที่มี WHT, และปรับ UX ให้ตรวจเอกสารได้ง่ายขึ้น

ข้อกำหนด #1: เอกสารมี WHT ให้แสดงสัญลักษณ์ "w" + คำนวณย้อนกลับกรณีข้อมูลไม่ครบ

ปัญหาจริง

  • ตัวอย่างเอกสาร 03062026130649.pdf มี WHT ชัดเจน แต่บางครั้งระบบไม่ผูกความสัมพันธ์ Gross / Paid / WHT ถูกต้อง
  • ผู้ใช้ต้องการสัญลักษณ์ที่มองเห็นเร็วว่าไฟล์นี้เป็นกลุ่ม WHT

สิ่งที่ต้องทำ

  • เพิ่ม badge w ในรายการเอกสารฝั่งซ้ายเมื่อพบ wht_amount > 0 หรือ has_wht = true
  • เพิ่มตัวแก้สมการย้อนหลังเมื่อมี gross + wht + paid แต่ net/vat ไม่ครบ เพื่อ backfill อย่างมีหลักฐาน
สูตรอ้างอิง: AmountPaid = Gross - WHT และ WHT = Net x WHTRate

ข้อกำหนด #2: ปรับ UX/UI ให้ Zone B (พื้นที่ดูเอกสาร) กว้างขึ้น 3 เท่า

ปัญหาจริง

  • หน้าจอ Review ปัจจุบันพื้นที่เอกสารค่อนข้างแคบ ทำให้ไล่ดูตัวเลขยาก

สิ่งที่ต้องทำ

  • เพิ่มโหมด Wide x3 ให้คอลัมน์เอกสารกว้างขึ้น (เช่น 75%) และคอลัมน์ฟิลด์ย่อเหลือ 25%
  • จำค่าโหมดใน local storage เพื่อใช้ต่อเนื่อง

ข้อกำหนด #3-4: แก้การสลับ inclusive/exclusive และความกำกวมคำว่า NET/TOTAL บนเอกสารไทย

ปัญหาจริง

  • เอกสารหลายแบบวาง label ไม่ตรง semantic บัญชี เช่นใช้คำว่า NET AMOUNT ในตำแหน่ง Gross
  • ผลคือระบบจัด layout VAT ผิด และคะแนนตกทั้งที่ภาพชัดมาก

Hint จากผู้ใช้ (ต้องนำไปใช้จริง)

  • แบบ บวก VAT (exclusive): ค่าบนมักน้อยกว่าค่าล่าง (ฐาน + VAT = ยอดรวม)
  • แบบ ถอด VAT (inclusive): ตรรกะกลับกันตามโครงสร้างยอดรวมที่รวม VAT อยู่แล้ว

สิ่งที่ต้องทำ

  • เพิ่ม arithmetic-first classifier: จัดลำดับตัวเลขและเลือกโมเดลที่สมการลงตัวก่อนเชื่อ label
  • เพิ่ม prompt guard เรื่อง Thai form wording เพื่อไม่ map ตามคำอังกฤษอย่างเดียว
  • เพิ่ม confidence policy ใหม่: ถ้าสมการลงตัวชัดเจนให้คะแนนไม่ตกเพราะ label ambiguity

ข้อกำหนด #5: เคสตัวเลขทับตาราง (grid overlap) ให้ preprocess ก่อน OCR

ปัญหาจริง

  • เอกสาร 03062026131847.pdf มีตัวเลขทับเส้นตารางทำให้ OCR เพี้ยนหนัก

สิ่งที่ต้องทำ

  • เพิ่ม pre-processing เพื่อลบเส้นแนวตั้ง/แนวนอนก่อน OCR (OpenCV morphology + line removal)
  • ถ้าเป็น PDF ดิจิทัล ให้ดึง text layer โดยตรงก่อน OCR เพื่อลด error

ข้อกำหนด #6: รองรับเอกสารเฉพาะกลุ่ม Broker ประกัน

ปัญหาจริง

  • โครงสร้างเอกสาร Broker ไม่เหมือนใบกำกับทั่วไป จึง map field และบัญชีไม่เข้า

สิ่งที่ต้องทำ

  • เพิ่ม route classifier สำหรับคำสำคัญเช่น Broker, นายหน้า, ประกันภัย
  • สร้าง extraction template และ posting rule เฉพาะกลุ่ม broker

ประเมิน Effort (เพื่อคิดราคา Requirement / Delivery Plan)

งาน รายละเอียด Effort (Dev Day) Complexity หมายเหตุราคา
#1 WHT Badge + Backfill Solver UI badge, rule engine/backfill, tests, edge-case validation 2.5 - 4.0 High ต้องมี test matrix หลายเอกสาร
#2 Zone B Wide x3 UX Layout toggle, responsive, state persistence 1.0 - 1.5 Low ทำคู่กับ usability review ได้
#3/#4 VAT Layout Disambiguation Arithmetic-first classifier, prompt guard, confidence policy tuning 4.0 - 6.0 Critical เป็น core accuracy ของ Phase II
#5 OCR Gridline Preprocess OpenCV preprocessing + fallback text-layer extraction 3.0 - 5.0 High ขึ้นกับคุณภาพ PDF/scan source
#6 Broker Template Route Doc classifier + broker template + posting rules 2.5 - 4.5 Medium-High ควรเก็บตัวอย่าง broker เพิ่ม
รวมประมาณ รวม dev + unit/integration tests + tuning รอบแรก 13.0 - 21.0 วัน Mixed ยังไม่รวม UAT และเปลี่ยน requirement กลางทาง
แนะนำคิดราคาเป็น 2 ก้อน:
  • Requirement & Design Package: 20-30% ของงบรวม
  • Implementation Package: 70-80% ตาม effort จริงและจำนวนรอบแก้

Acceptance Criteria (ฉบับสั้นสำหรับคุยกับผู้ใช้)

  • เอกสารมี WHT แสดง badge w ใน list ทุกไฟล์ที่เข้าเงื่อนไข
  • โหมด Zone B Wide x3 เปิด/ปิดได้ และจำค่าผู้ใช้ได้
  • ลด false layout (inclusive/exclusive) อย่างน้อย 80% บนชุดเอกสารที่เคยผิด
  • เคสตัวเลขทับตาราง OCR accuracy ดีขึ้นแบบวัดได้ (ก่อน-หลัง)
  • เอกสาร broker ผ่าน extraction + posting rule ขั้นพื้นฐานได้
